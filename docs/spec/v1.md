# BhayanakShare version 1 spec

Status: **approved** (2026-10-04). Built from the wayfinder map [#1](https://github.com/theHimanshuShekhar/bhayanakshare/issues/1); every section links the ticket that decided it. Terms are defined in [`CONTEXT.md`](../../CONTEXT.md). Items marked *(assumption)* were routine calls made without a user decision and are the first things to challenge in review.

## 1. Scope

BhayanakShare is a desktop app for sending files, folders and text directly from one Device to another, AirDrop-style, over LAN or the internet. ([#2](https://github.com/theHimanshuShekhar/bhayanakshare/issues/2))

**In version 1**
- Windows, macOS and Linux desktop. Research, benchmarks and tests run on Linux only; Windows and macOS are assumed to work.
- Per-Device identity; one-sided Contacts with optional per-Contact Auto-accept (off by default).
- Choosing Receivers from Contacts, Nearby Devices, or a pasted Device ID / link / QR.
- Files, folders (structure kept) and text; multi-Receiver sends (Batches).
- LAN and internet, through n0's public relays.
- Resume across restarts and crashes.
- Tray and background running, Transfer History, Device ID sharing by link and QR, auto-update.

**Out of scope:** mobile apps (permanently); store-and-forward to offline Receivers (the send fails immediately); clipboard sync; Flatpak; self-hosted relay/DNS; manual pause; Claude Design work (a separate effort that starts from section 7).

**Technology:** Tauri 2 + React + TypeScript + Vite; Rust core on iroh 1.x; content via iroh-blobs pinned to an exact version ([ADR 0001](../adr/0001-iroh-blobs-for-transfer-content.md)).

## 2. Identity and Contacts ([#9](https://github.com/theHimanshuShekhar/bhayanakshare/issues/9))

- **Device ID** is the iroh `EndpointId`, shown as 52-character base32. Its **Fingerprint** is the first 8 characters, displayed as `K3QF-7XNA`, used only for checking by eye.
- **Share link:** `bhayanakshare://add/<base32 ID>?name=<suggested name>`; the QR code encodes the link. The suggested name is editable when adding.
- **Contacts** are matched by Device ID and badged. A Contact is shown under its **Nickname** if set, else its current Device Name, which refreshes whenever the Devices connect or see each other's beacon.
- **Non-Contacts** always show name · Fingerprint, in Nearby and in Offers. Saving one as a Contact asks the user to check the Fingerprint with its owner.
- **Secret key:** OS secret store (Secret Service on Linux), falling back to a 0600 file. Settings → Export identity writes a password-protected file (Argon2id *(assumption)*); Import replaces this Device's identity after a warning. Contacts and History are not exported. Losing the key without an export means a new Device ID.
- Each Contact stores a **last known address** (relay URL + direct addresses) ([#16](https://github.com/theHimanshuShekhar/bhayanakshare/issues/16)).

## 3. Discovery and reachability

**Visibility** ([#3](https://github.com/theHimanshuShekhar/bhayanakshare/issues/3), [#19](https://github.com/theHimanshuShekhar/bhayanakshare/issues/19)), default **People who have my ID**:

| Setting | LAN broadcast | Who sees the Device Nearby | Device Name visible to |
|---|---|---|---|
| Everyone | Plain announcement with name | Anyone on the LAN | Anyone on the LAN |
| People who have my ID | Rotating blinded beacon keyed on the Device ID, on `swarm-discovery` with our own service name | Devices holding the ID | ID holders |
| Hidden | Nothing; a custom responder answers LAN lookups from ID holders only | Nobody | ID holders |

Visibility governs discovery only: anyone holding the Device ID can send to it. Accepted limitation: anyone who dials the UDP port learns the Device ID from the TLS handshake. No Device Name or `UserData` is ever published to n0 DNS or the DHT.

**Dialling a Contact over the internet** ([#5](https://github.com/theHimanshuShekhar/bhayanakshare/issues/5), [#16](https://github.com/theHimanshuShekhar/bhayanakshare/issues/16)): cached last known address first, then n0 DNS (`dns.iroh.link`) and the Mainline DHT in parallel. Both publish and lookup use the DHT, on by default, with a Settings toggle. Relays are n0's public relays; relay URLs stay configurable. Relay rate limiting slows a Transfer but doesn't drop it.

## 4. Transfer lifecycle ([#6](https://github.com/theHimanshuShekhar/bhayanakshare/issues/6), [#7](https://github.com/theHimanshuShekhar/bhayanakshare/issues/7))

**Sender:** Offered → Declined | Expired | Cancelled, or Accepted → Waiting → Transferring → Completed | Failed | Cancelled. *Preparing* overlays Offered/Accepted while hashing.

**Receiver:** Offered (or Auto-accepted) → Declined | Expired | Cancelled, or Accepted → Waiting → Transferring (*Reconnecting* while retrying) → Saving → Completed | Failed | Cancelled.

- The Offer is sent immediately; the Sender hashes while the Receiver decides, and sends `HashReady` once hashing is done and the Receiver has accepted, after allowing that Receiver to fetch. An earlier `HashReady` would race that grant: the Receiver could dial the provider before the Sender had read its `Accept`.
- An unanswered Offer expires after **10 minutes**. A pending Offer does not survive a Sender restart *(assumption)*.
- A stalled Transfer expires **24 hours after its last progress**; the Receiver then deletes partial data.
- Either side can cancel until the Receiver starts Saving, because the move into the save folder can't be undone *(assumption)*. No manual pause.
- **Resume:** the Receiver drives it, redialling with backoff (fast, then about once a minute). One fetch per Transfer; after a crash iroh-blobs re-hashes partial data and continues. A kill in the first ~1 s of a fetch loses that second's data ([#18](https://github.com/theHimanshuShekhar/bhayanakshare/issues/18)).
- **Persisted:** Sender keeps the Transfer record, Offer, content hash and each source file's path, size and mtime; Receiver keeps the Transfer record and its incoming store.
- **Source changes:** before serving, the Sender checks size and mtime; a changed or missing file fails the Transfer with "A file changed on the sending Device: <name>".
- **Delivery:** nothing reaches the save folder until everything is received and verified; then the whole set is moved in (Saving). Cancelled or failed Transfers leave nothing there.

**Batches** ([#7](https://github.com/theHimanshuShekhar/bhayanakshare/issues/7)): one Transfer per Receiver; Receivers never learn of each other. The Sender sees one expandable row and one History entry; can cancel one Receiver or all; can retry a Failed (not Declined) Transfer inside the Batch with a new Offer. At most **3** Receivers download at once; others show Waiting.

## 5. Control protocol ([#8](https://github.com/theHimanshuShekhar/bhayanakshare/issues/8))

- Own ALPN `bhayanakshare/ctrl/1`; length-prefixed postcard frames on one bidirectional stream per Transfer *(assumption)*.
- First message each way: `Hello { protocol_version, app_version }`. Incompatible versions are refused before any Offer; both sides see who must update, and the older side gets "Update now". The iroh-blobs version is pinned exactly; changing it bumps `protocol_version`.

| Message | Direction | Notes |
|---|---|---|
| `Hello` | both | Version check |
| `Offer` | S→R | Transfer ID (random 128-bit), kind, manifest or inline text, total size, file count, skipped-symlink count. The 10-minute expiry is a fixed protocol constant, timed by each side from when it sent or received the Offer |
| `HashReady { collection_hash }` | S→R | After `Accept` and hashing are both done |
| `Accept` / `Decline` | R→S | Decline carries no reason |
| `Busy` | R→S | Automatic: 5 pending Offers from this Sender already *(assumption)*. The Sender shows it as Failed with a "too many Offers" reason |
| `Cancel` | both | Accepted until the Receiver starts Saving; the move into the save folder can't be undone |
| `Expired` | both | While the Offer is unanswered; sent by the side whose timer fires first, so the other shows Expired rather than "went away" |
| `Resume { transfer_id }` → `ResumeOk` / `Unknown` / `Failed { reason }` | R→S | After reconnect |
| `Failed { SourceChanged { path } }` | S→R | |
| `Completed` | R→S | After verification, export and fsync |

- **Manifest:** relative paths, sizes, mtimes, executable bit, empty folders. Symlinks are skipped and counted; ownership and other permissions are not sent. The iroh-blobs Collection's names must match the manifest's file list exactly *(assumption)*.
- **Text:** up to 64 KiB UTF-8 inline in the Offer; larger text is sent as a file named `text.txt` *(assumption)*.
- **Limits** *(assumption)*: 500,000 entries, 64 MiB encoded Offer, 4,096-byte paths, 255-byte names.
- **Access control:** the Sender serves a Transfer's hashes only to that Transfer's accepted Receiver, and rejects every other request kind (section 8).
- **Receiver checks:** free space and path length against the save folder. A failing check still shows the prompt with a warning and Accept disabled; such Offers are never auto-accepted.

## 6. Received names ([#17](https://github.com/theHimanshuShekhar/bhayanakshare/issues/17))

- An Offer is rejected as malformed if any path is absolute, contains `..`/`.`/empty segments, NUL, control characters or a backslash separator, or exceeds the limits.
- Windows-invalid names are adjusted identically on every OS: `< > : " | ? *` → `_`; trailing dots/spaces trimmed (empty → `_`); reserved device names get a `_` suffix on the stem. The prompt and History show "N names adjusted".
- Case-only clashes within a Transfer: the later entry gets " (1)" *(assumption)*.
- Clashes with existing items: each top-level item is renamed as a unit — `photos (1)/`, `a (1).txt` — never merged or overwritten.
- Over-long final paths disable Accept on Linux/macOS; Windows uses `\\?\` paths (untested).

## 7. User flows ([#12](https://github.com/theHimanshuShekhar/bhayanakshare/issues/12), [#10](https://github.com/theHimanshuShekhar/bhayanakshare/issues/10), [#11](https://github.com/theHimanshuShekhar/bhayanakshare/issues/11))

**First run:** one screen — Device Name (prefilled with hostname), Visibility (default People who have my ID), start at login (on). Save folder defaults to `~/Downloads/BhayanakShare`.

**Home (Devices first):** a grid of Contacts (badged, first), Nearby non-Contacts (name · Fingerprint), and a "Send to ID…" tile. Tiles show online/nearby status and in-flight Transfers. Empty state offers the user's link/QR and, after 30 s, a firewall hint. Tabs: Home · History · Contacts · Settings; "My ID" shows link, QR and Fingerprint.

**Sending:** drop onto a tile, or select tiles → Send (file/folder picker) or Text. Several tiles form a Batch. Sender sees the states in section 4 and errors: version mismatch, unreachable, invalid names, Busy, symlinks skipped.

**Receiving:** if hidden, an OS notification (no action buttons) opens the window on the Offer. The Offer sheet shows Sender identity, items, total size, save folder (changeable), warnings (space, adjusted names, long paths), a 10-minute countdown, and Accept / Decline. Auto-accept skips the sheet unless a warning applies and notifies on completion. Completed items offer Show in folder or Copy (text).

**History:** kept until the user deletes entries or clears it. Records direction, Batch, other Device (ID and name at the time), times, kind, item names, counts, size, adjusted names, final state with reason, saved location, and full text for text Transfers — never file content. Filter by Device and direction, search, per-Contact view, expandable Batches; actions Show in folder, Copy, Retry, Delete.

**Contacts:** Nickname, Device Name, Fingerprint, Auto-accept, history link; add by link/ID/QR/deep link/"Save as Contact"; removing keeps History.

**Settings:** Device Name, My ID; Visibility, public DHT; save folder; start at login, updates; export/import identity; debug logging, export diagnostics.

**Background:** closing goes to the tray (one-time notice); start at login on by default; single instance, with a second launch focusing the window and passing files to the send flow. Tray menu: Open, Send files…, Visibility, Quit — nothing relies on clicking the icon, since Linux has no click events. Quitting with active Transfers asks to confirm, then shows "Saving progress…" for up to 30 s.

## 8. Architecture ([#13](https://github.com/theHimanshuShekhar/bhayanakshare/issues/13))

Verified against iroh 1.3.0, iroh-blobs 0.103.0, iroh-mainline-address-lookup 0.6.0, swarm-discovery 0.6.3 and Tauri 2.12.

- **Layout** *(assumption)*: `crates/core` (Rust, no Tauri dependency: endpoint, discovery, control protocol, state machines, stores, persistence; all integration tests run here); `src-tauri` (thin shell: commands, event forwarding, tray, notifications, deep links, autostart, single instance, updater); `ui` (React). Typed commands from UI to core and one event stream back, with TypeScript types generated from Rust (`specta`).
- **Persistence** *(assumption)*: SQLite (WAL) in the app data folder for settings, Contacts, Transfer records and History. The secret key lives in the OS secret store.
- **Sender store:** one global iroh-blobs fs store; files imported by reference, so it holds only outboards.
- **Receiver store:** one per Transfer at `<save folder>/.bhayanakshare-incoming/<transfer id>/`, always on the save folder's filesystem, so Saving is a rename. Deleted after Saving, failure or cancellation; exported files and folders are fsynced before `Completed`. Stores are opened only while active (each starts its own runtime), and core never opens one directory twice (a second open hangs). ~800 MiB RSS for 100k-file Transfers (redb's fixed cache) is accepted.
- **Provider access control (security requirement):** intercept `connected` and `get`; map connection to EndpointId from `ClientConnected`; allow GET only for hashes of a Transfer this Receiver accepted (only the Transfer's root hash is served, for as long as the Transfer runs); **explicitly reject PUSH, GET_MANY and OBSERVE**, which iroh-blobs 0.103 gates on `mask.get` (without a hook, any peer can PUSH into the store). Covered by a regression test; worth reporting upstream.
- **Discovery:** `presets::N0` + `DhtAddressLookup` (relay URLs only), queried concurrently; a wrapper service implements the DHT toggle; Contacts' last known addresses via a memory lookup; `UserData` never set. LAN uses `swarm-discovery` with our service name, beacon in TXT. **Hidden needs a small custom mDNS responder** that answers only a query carrying a blinded token of its own ID.
- **Logging:** `tracing` to rotating files (info, ~7 days / 50 MB), debug toggle, Export diagnostics zip. Device IDs logged as Fingerprints; file names and text never logged; no telemetry.
- **Linux plugin notes:** single-instance (DBus) registered first with its `deep-link` feature; deep-link calls `register_all()` at startup so a moved AppImage re-registers; tray is menu-only.

## 9. Packaging and updates ([#14](https://github.com/theHimanshuShekhar/bhayanakshare/issues/14))

- Linux: AppImage, deb, rpm via Tauri's bundler. No Flatpak.
- Updates: Tauri's signed updater against GitHub Releases, checking at startup and daily, installing on restart after consent. deb/rpm show a notice with a link. A version-mismatch refusal offers "Update now". The update-signing key lives only in CI secrets.
- Linux firewall: docs explain allowing mDNS and the app's UDP port on firewalld; packages don't change firewall rules; the Nearby empty state links to the docs.
- Windows/macOS: Tauri default bundlers. Code signing, notarisation, Windows Firewall rules and the macOS Local Network permission are **release prerequisites**, not v1 design work.

## 10. Quality baseline *(assumptions — previously unspecified fog)*

- **Performance** (from [#18](https://github.com/theHimanshuShekhar/bhayanakshare/issues/18), Linux, loaded disk): Sender import by reference of 10 GiB in about a minute cold; about 5,000 small files/s for import and fetch; LAN throughput limited by disk, not protocol. No hard throughput target for relayed Transfers, which n0 rate-limits.
- **Tests** (Linux only): unit tests for name sanitisation, manifest validation, the state machines and protocol encoding; two-Device integration tests in one process over localhost covering accept/decline/cancel/expiry, Batch, version mismatch, resume after clean stop and after kill -9, and source-file change; a two-Device LAN discovery test per Visibility setting; a throttling test against a self-hosted `iroh-relay` with a low limit.
- **Error messages:** every terminal or warning state in sections 4–7 gets one plain-language sentence naming the cause and, where possible, the fix. The catalogue is written with the Claude Design work.
- **Accessibility:** full keyboard operation, visible focus, screen-reader labels on every control, progress announced through ARIA live regions, and no information conveyed by colour alone.
- **Localisation:** English only in v1; all UI strings go through a translation layer so more languages can be added later.
